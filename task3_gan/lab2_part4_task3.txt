OVERVIEW
----------------------------------------------------------------------
Goal (optional hard-tier task, on top of Tasks 1 and 2): generate
realistic, diverse brain MRI slices from noise using a GAN, with mode
collapse fully resolved and evidence of training provided (generated
images, loss plots).

Approach chosen: WGAN-GP (Wasserstein GAN with Gradient Penalty)
rather than a vanilla DCGAN, specifically for training stability --
deliberately the more complex option, chosen upfront knowing it would
need more explaining but reduce the risk of the exact failure mode
(mode collapse) the lab explicitly warns about and grades on.

Environment: Rangpur HPC. MNIST prototype ran on the cpu partition
(no GPU needed for a 32x32 smoke test); OASIS training ran on the
comp3710 GPU partition.


THE STORY (CHRONOLOGICAL)
----------------------------------------------------------------------
1. Explained WGAN-GP's mechanics before writing code: critic (not
   "discriminator" -- outputs a raw score, no sigmoid) trained to
   maximise E[critic(real)] - E[critic(fake)]; generator trained to
   maximise E[critic(fake)]; a gradient penalty term keeps the critic
   close to 1-Lipschitz, which the underlying Wasserstein-distance
   approximation requires to be mathematically valid; critic trained
   5 steps per 1 generator step (standard ratio); no BatchNorm in the
   critic specifically, since it interacts badly with the per-sample
   gradient penalty (InstanceNorm used instead); Adam with
   beta1=0, beta2=0.9 (the WGAN-GP paper's specific recommendation,
   notably different from a vanilla DCGAN's typical beta1=0.5).

2. Phase A: prototyped on MNIST (resized to 32x32) first, deliberately,
   rather than debugging directly on OASIS -- MNIST trains in
   seconds/minutes and gives an unambiguous "did recognisable digits
   form" signal, versus OASIS where a bug and "just needs more
   training" would be much harder to tell apart.

3. First MNIST attempt ran far slower than expected (15+ minutes with
   no epoch completed) -- diagnosed as the job only being allocated 1
   CPU core by default while PyTorch's CPU conv operations need
   multiple threads to run efficiently. Fixed with
   --cpus-per-task=4 and an explicit torch.set_num_threads() call
   reading the Slurm-allocated CPU count.

4. Ran a fast MNIST smoke test (5000-image subset, 10 epochs, ~780
   generator updates total). Result: critic loss stayed bounded and
   stable (~-24 to -25, no NaN/explosion) -- strong evidence the loop
   mechanics (gradient penalty, loss signs, update ratio) were
   implemented correctly. Generator loss and the Wasserstein estimate
   both moved in the "wrong" direction over these 10 epochs, but this
   was expected: with 5 critic updates per 1 generator update, the
   critic normally races ahead early before the generator has had
   enough updates to catch up.

5. Sample images showed no digit-like structure and looked unchanged
   across epochs -- at the time interpreted as "just needs far more
   than 780 generator updates," which published WGAN-GP results
   support (typically thousands of updates needed).

6. Decision made explicitly: rather than spend more CPU wall-clock
   time chasing digit formation on a dataset that isn't graded,
   treated the "no bugs, stable losses" result as sufficient
   validation and moved to Phase B (OASIS on GPU), reasoning that any
   remaining "does it actually converge" uncertainty would need to be
   answered on OASIS regardless, since that's the graded target.

7. Phase B: ported the architecture to 64x64 (one more up/downsampling
   stage than the MNIST version), unconditional generation on raw
   OASIS training images (no segmentation masks needed), with
   in-memory data preloading applied proactively (same lesson learned
   from an earlier UNet optimisation) and checkpoint/resume support
   added upfront in case one job's time limit wasn't enough.

8. Trained 100 epochs (~15,100 generator updates) on the full 9664-
   image training set. Wasserstein estimate dropped sharply for the
   first ~20 epochs (28.0 -> 3.2, looking very promising), then drifted
   slowly upward for the remaining 80 epochs (3.2 -> 4.3), while
   generator loss grew increasingly negative without bound.

9. IMPORTANT: the saved sample images looked like near-identical
   vertical stripe patterns across epoch 10, 50, and 100, and even in
   the random-noise diversity check -- initially read as a serious
   problem (no structure forming despite 15,000+ updates). Investigated
   and found the actual cause: a genuine bug in the visualisation code,
   not the model. After reshaping a batch of generated images into a
   grid array, an extra `[0]` index was accidentally selecting only
   the TOP ROW of pixels from each generated image, then broadcasting
   that single row down across the whole tile -- producing exactly the
   vertical-stripe artifact seen, regardless of what the generator was
   actually producing. This explains why MNIST's earlier "no digits"
   result was ALSO inconclusive -- same bug, same script pattern.

10. Fixed the indexing bug (removed the erroneous `[0]`) and, since
    the trained generator weights were never wrong -- only the
    rendering of them -- wrote a small script to regenerate correct
    sample images directly from the existing checkpoint, with NO
    retraining needed. This ran in under 15 seconds.

11. Result: the corrected images showed clearly realistic,
    anatomically plausible brain slices with genuine diversity across
    both the fixed-noise and random-noise grids -- different ventricle
    shapes and sizes, different skull outlines, different brightness
    levels, no mode collapse.

12. Honest limitation identified and disclosed rather than hidden:
    the checkpoint file was overwritten at each save rather than kept
    per-epoch, so only the final epoch-100 generator weights survive
    -- meaning the earlier upward drift in the Wasserstein estimate
    (step 8) can be confirmed as harmless (final quality is good) but
    NOT proven to have never dipped below an earlier peak, since no
    intermediate correctly-rendered checkpoint exists to compare
    against.

LIKELY TUTOR QUESTIONS AND ANSWERS
----------------------------------------------------------------------
Q: What is a GAN, and what specifically does WGAN-GP change versus a
   standard one?
A: A GAN trains a generator and a discriminator/critic against each
   other -- the generator tries to fool the critic, the critic tries
   to catch fakes. Standard GAN loss (binary cross-entropy) can give
   vanishing or exploding gradients depending on how confidently the
   critic is winning, which is a major source of GAN training
   instability. WGAN-GP instead approximates Wasserstein (Earth
   Mover's) distance between real and fake distributions, which gives
   smoother, more informative gradients throughout training, at the
   cost of needing a gradient penalty term to keep the critic
   approximately 1-Lipschitz (a mathematical requirement for the
   Wasserstein approximation to be valid).

Q: Why train the critic 5 times per generator update?
A: The Wasserstein distance estimate is only meaningful if the critic
   is close to optimal at each step; training it more per generator
   update keeps it closer to that ideal throughout training. This is
   the ratio recommended in the original WGAN-GP paper.

Q: Why no BatchNorm in the critic?
A: The gradient penalty is computed per-sample (on individual
   interpolated images between real and fake), but BatchNorm mixes
   statistics across the whole batch, which conflicts with that
   per-sample computation. InstanceNorm was used instead, since it
   normalises each sample independently.

Q: What is mode collapse, and how did you check for it?
A: Mode collapse is when the generator finds one (or very few) outputs
   that reliably fool the critic and just produces variations of that,
   rather than the full diversity of real data. Checked directly with
   a grid of 64 images from 64 DIFFERENT random noise vectors --
   genuine collapse would show up as most/all of those 64 looking
   near-identical; ours showed clear variation in ventricle shape,
   brain outline, and brightness across all 64.

Q: Why prototype on MNIST first if it ended up being inconclusive
   anyway?
A: It wasn't actually inconclusive on the question it was meant to
   answer -- it confirmed the training loop itself was numerically
   stable (no NaN, no exploding losses), which is the thing most
   likely to be subtly wrong in a first WGAN-GP implementation. The
   "no digits visible" observation turned out to be caused by a
   separate visualisation bug, discovered later, unrelated to whether
   MNIST prototyping was a good idea.

Q: Walk me through the visualisation bug you found.
A: After generating a batch of images and reshaping them into a grid
   layout for a combined image, the code indexed one extra dimension
   too far -- `grid[i, j, 0]` when `grid[i, j]` was already the
   complete 2D image. That extra index took just the top row of
   pixels from each image, and broadcasting that single row across a
   larger canvas block produced vertical stripes -- visually
   consistent with what we saw regardless of epoch, since the
   underlying bug was the same at every point in training.

Q: Why didn't you retrain after finding the bug?
A: The generator's actual learned weights were never affected by the
   bug -- only the code that rendered them into a picture was wrong.
   So the fix was to correct the rendering code and re-run inference
   (a single fast forward pass) using the already-trained checkpoint,
   rather than repeating ~35 minutes of GPU training for no reason.

Q: Why does the Wasserstein estimate drift upward late in training,
   and are you sure quality didn't get worse?
A: The gradient penalty only enforces the critic stays approximately
   1-Lipschitz LOCALLY, not that its absolute output scale stays
   fixed -- so critic/generator loss magnitudes can drift over long
   training without that drift necessarily meaning image quality is
   degrading. We can confirm quality is good at epoch 100 (the
   corrected final images), but we cannot rule out that an earlier
   epoch, like 40 or 60, was actually better, because the checkpoint
   file was overwritten at every save and no intermediate correctly-
   rendered snapshot survived. This is an honest, acknowledged gap,
   not something we're claiming to have verified.

Q: How would you fix that limitation if asked to improve this
   further?
A: Save versioned checkpoints (e.g. checkpoint_epoch_010.pt,
   checkpoint_epoch_020.pt, ...) instead of overwriting a single
   checkpoint.pt file, so the full training trajectory could be
   inspected and compared after the fact, not just the final state.


Critic:
Channel count does mostly increase as the grid shrinks (1→64→128→256→512) — but the very last layer 
collapses all the way down to just 1, and that's the important part to fix:
The critic does not output a "vector" or a per-pixel grading map. The final layer 
(512 → 1 channel, 4×4 kernel, stride 1, on a 4×4 input) produces exactly one number for the entire 
image — not one score per pixel. Think of it like the encoder side of the VAE or UNet: 
early layers see fine detail, deep layers see broad context, and by the end everything has been 
boiled down to a single, whole-image verdict: "how real does this entire image look, overall?"

Critic starts at 64×64 with 1 channel — raw pixels, maximum fine-grained visual detail, 
but each individual conv position only "sees" a tiny patch, no big-picture sense of the whole 
image yet. By the end, it's collapsed to a single number — all that detail has been consolidated 
into one broad, whole-image verdict. So the critic's real direction is: fine/detailed → abstract/broad

critic_loss = -(critic_real - critic_fake) + LAMBDA_GP * gp
The critic is trained to maximize critic_real - critic_fake — meaning it wants critic(real) 
to go up and critic(fake) to go down. So a high score is the critic saying "this looks real" — 
real images are what get pushed toward high scores, always. It's not "high = fake" on some fakeness scale; 
it's "high = convincing," full stop, and the critic is trying to reserve high scores for genuine real images only.

a standard discriminator's sigmoid output can get extremely close to 0 or 1 when it's very confident — 
and right at those extremes, the sigmoid function's slope goes nearly flat. A flat slope means almost 
no gradient signal reaches the generator ("vanishing gradients") — the generator gets told "you're wrong" but 
with almost no useful information about how wrong or which direction to move. The critic's raw, unbounded 
score never flattens out like that — it can keep providing a meaningful, non-vanishing gradient no matter how 
confidently it's currently rating something.

Generator:
gen_loss = -critic(fake).mean()
The optimizer minimizes gen_loss. Minimizing -critic(fake) is mathematically the same as 
maximizing critic(fake) — so the generator is trying to push its own fakes' scores up, not down. 
The generator wants the critic to rate its fakes highly (fooling it into thinking they're real), 
and the critic is simultaneously trying to keep pushing fake scores back down.
Generator starts at 4×4 with 512 channels — this is the most abstract, 
most compressed state (tiny grid, many abstract "concepts" encoded per location, but almost 
no visible spatial structure yet — you couldn't look at this and see a brain). By the end, 
it's 64×64 with 1 channel — every one of those abstract concepts has been "cashed in" and 
converted into actual, visible pixel-level detail. So the real direction is: 
abstract/broad → fine/detailed, not the other way around.



BCE → Wasserstein loss is the fix for the vanishing/unstable gradient problem (critic gets too confident, 
generator gets no useful signal). This swap alone is what "WGAN" (without the "-GP") already does.
Wasserstein distance measures the difference between two probability distributions 
by calculating the minimum "cost" required to transform one distribution into the other. 
The critic's loss (critic_real − critic_fake, which it tries to maximize) 
is a mathematical approximation of that distance between the two distributions. 
As training progresses and the generator improves, that distance should shrink toward zero — 
meaning "the generator's distribution and the real distribution are becoming hard to tell apart."

Gradient penalty: the math behind Wasserstein distance only works correctly if the critic function 
is "1-Lipschitz" (a smoothness constraint — the function can't change output faster than a 1:1 rate relative 
to how much its input changes). Switching to Wasserstein loss doesn't automatically give you that 
smoothness; you have to enforce it separately, and gradient penalty is the mechanism that does the enforcing.

Not "prevents the critic from jumping too high" — the raw score is allowed to be any value,
no ceiling. What it actually constrains is how fast the score is allowed to change as you 
nudge the input image slightly — that's what "1-Lipschitz" precisely means: the critic's output 
can't change faster than a 1-to-1 rate relative to how much the image itself changed. This constraint 
has to be enforced specifically because the Wasserstein-distance math only gives a valid, meaningful 
distance estimate when the critic obeys that smoothness rule — without it, the critic could make 
its scores arbitrarily steep, and the "distance" it reports would stop meaning anything real.


Normalisation Layers:
A normalization layer takes whatever numbers come out of the previous conv layer and 
rescales them to have a mean of 0 and a standard deviation of 1, before the next layer sees them. 
This keeps activation values from drifting to huge or tiny magnitudes as they pass through many 
layers, which makes training much more stable.
difference between BatchNorm and InstanceNorm is which numbers get averaged together to compute that mean/std:
BatchNorm: computes one mean and one std per channel, but averaged across every
 image in the current batch simultaneously. Image A's normalization is influenced by what
  images B, C, D... in the same batch look like.
InstanceNorm: computes a separate mean and std per image, per channel, using only that
 single image's own pixels. Image A's normalization depends only on image A — no cross-contamination
  with anything else in the batch.

the whole gradient penalty calculation is built on the idea of treating each interpolated
image completely independently — computing "how does the critic's score change if I nudge this 
one image slightly." If BatchNorm is in the mix, that image's actual output is quietly influenced 
by whatever else happens to be sitting in the same batch




WGAN-GP — QUICK REFERENCE (Task 3)

GENERATOR (5 ConvTranspose2d layers):
- Input: 100 random numbers (noise vector z)
- Starts abstract/compressed: 4x4 grid, 512 channels
- Each layer: channels DECREASE, grid size INCREASES (stride 2)
- Ends fine/detailed: 64x64 grid, 1 channel, Tanh activation
- Direction: abstract concepts -> cashed in as visible pixel detail

CRITIC (5 Conv2d layers) — mirror image of generator:
- Input: 64x64 image (real or fake), 1 channel
- Starts fine/detailed: raw pixels, small receptive field
- Each layer: channels INCREASE, grid size DECREASES (stride 2)
- Ends abstract/consolidated: single raw score (not per-pixel, not a vector)
- Direction: fine detail -> one whole-image verdict

CRITIC OUTPUT:
- One raw, UNBOUNDED number per image (no sigmoid)
- HIGH score = critic is confident the image is REAL
- Critic trained to maximize: critic(real) - critic(fake)
  -> pushes real scores up, fake scores down
- Generator trained to maximize critic(fake)
  -> tries to push its own fakes' scores up
- That opposing push is the whole adversarial dynamic
One critic score (what you get from critic(single_image)) is just that one image's individual "how real does this look" rating
The actual Wasserstein distance estimate is the difference between two averages
average score across a batch of REAL images -
average score across a batch of FAKE images

WHY NOT BCE (standard GAN loss):
- Sigmoid output can saturate near 0 or 1 when critic is very confident
- Near those extremes, sigmoid's slope is nearly flat -> vanishing gradients
- Generator gets "you're wrong" with almost no usable direction/magnitude
- Raw unbounded critic score never flattens like that -> gradient stays useful

WASSERSTEIN DISTANCE (plain version):
- "Earth Mover's distance" — the minimum "work" to reshape one distribution
  into another (move the least dirt, the shortest distance)
- Real images = distribution A, generator's outputs = distribution B
- critic_real - critic_fake approximates the distance between A and B
- As generator improves, this distance should shrink toward 0
- Stays mathematically meaningful even early in training when real/fake
  look very different — BCE's weak spot

GRADIENT PENALTY:
- Enforces the critic to be "1-Lipschitz"
- NOT about capping how high the score can go
- Controls HOW FAST the score can change as the input image changes
  slightly (rate of change, not magnitude of output)
- Required because Wasserstein distance is only a valid/meaningful
  estimate if the critic obeys this smoothness constraint
- Computed on random blends between real and fake images ("interpolates"),
  penalizing the gradient norm for straying from exactly 1

WHY INSTANCENORM, NOT BATCHNORM (in the critic):
- Both rescale activations to mean 0, std 1 — keeps values from
  exploding/shrinking across layers, stabilizes training
- BatchNorm: normalizes using stats averaged ACROSS the whole batch
  -> one image's output is influenced by other images in the same batch
- InstanceNorm: normalizes using stats from ONLY that single image
  -> every image's path through the network is fully independent
- Gradient penalty needs each interpolated image treated independently
  -> BatchNorm would violate that; InstanceNorm keeps it clean
- (First critic layer uses no normalization at all, by convention)
